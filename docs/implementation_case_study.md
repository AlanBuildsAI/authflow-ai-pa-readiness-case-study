# Implementation Case Study — Plenara

A professional synthetic healthcare operations SaaS prototype for prior
authorization, provider onboarding, and revenue-cycle readiness.

> Synthetic / mock data only. No PHI, no real patient/provider/payer/claims data,
> no integrations, and no production deployment. Human-in-the-loop workflow
> support — not clinical decision support and not approval/denial prediction.

## Problem

Healthcare operations teams manage prior authorization, provider onboarding, and
lab-claim readiness across disconnected systems, spreadsheets, and inboxes. Time
is lost figuring out what is blocked, why, who owns it, and what to do next.
Fragmentation causes rework, aging work, and preventable submission friction.

## Target stakeholders

Prior authorization managers · revenue cycle / billing managers · clinic
operations managers · provider onboarding teams · healthcare data / operations
analysts.

## Synthetic data model

Three deterministic, seeded synthetic datasets ([`data/`](../data)):

- `synthetic_authorization_cases.csv` — one synthetic PA case (90 rows)
- `synthetic_provider_onboarding.csv` — one synthetic provider-clinic-payer record (120 rows)
- `synthetic_claim_readiness.csv` — one synthetic diagnostic/lab claim (150 rows)

Every row is flagged `synthetic_only_flag = true`, contains no PHI-like columns,
and is regenerated by `python -m plenara.sample_data`.

## Three workflows

1. **Prior Authorization Readiness** — is a synthetic PA packet complete enough to submit?
2. **Provider / Clinic / Insurance Onboarding Readiness** — is a synthetic provider-clinic-payer relationship ready for operational use?
3. **Diagnostic / Lab Revenue Cycle Readiness** — is a synthetic diagnostic/lab claim ready for clean submission?

All three share one vocabulary: **READY / NEEDS REVIEW / BLOCKED**.

## Readiness logic

Deterministic, human-readable rules in the `plenara` package
([`readiness.py`](../src/plenara/readiness.py),
[`provider_onboarding.py`](../src/plenara/provider_onboarding.py),
[`claims_readiness.py`](../src/plenara/claims_readiness.py)). BLOCKED = a critical
requirement fails; NEEDS REVIEW = a softer signal needs a human; READY = checks
pass. No opaque scoring and no prediction.

## SQL analytics layer

- Metric definitions in [`analytics/metric_definitions.yml`](../analytics/metric_definitions.yml).
- dbt-style models in [`analytics/sql/`](../analytics/sql) (staging → fact → marts).
- A runnable **DuckDB SQL portfolio** ([`scripts/run_sql_portfolio.py`](../scripts/run_sql_portfolio.py))
  that answers eight business questions and writes CSVs to
  [`sample_outputs/sql/`](../sample_outputs/sql). See [`docs/sql_portfolio.md`](sql_portfolio.md).
- A consistency check proves the SQL-derived readiness matches the Python engines.

## Dashboard / command center

A Streamlit app organized as an operations command center: a **Product demo**
walkthrough, **Command center** KPIs + top actions, **Executive insights**, a
unified **Work queue**, per-module readiness views, **Data quality**, an
**Analytics layer**, and a **Safety** tab. A scenario selector switches the
synthetic operating posture.

## Data-quality checks

[`data_quality.py`](../src/plenara/data_quality.py) validates structural integrity
(no duplicate IDs, valid statuses, sane numeric ranges, owned blocked items) and
synthetic safety (no PHI-like columns, `synthetic_only_flag` present). The same
checks are asserted in the test suite.

## Business value demonstrated

- One explainable readiness picture across three workflows.
- Prioritized, owned work queue with recommended next actions.
- Executive KPIs and data-derived insights for leadership.
- SQL-backed metrics an analyst can reproduce and extend.
- Data-quality and synthetic-safety guarantees.

## Human-in-the-loop design

Plenara surfaces readiness states and recommended next actions to help people
prioritize. Every decision stays with a human — the system never submits,
approves, denies, or makes clinical/billing decisions.

## Safety boundaries

Synthetic-only; no PHI; no EHR/payer integrations; no claim submission; no
network calls at runtime; no production auth/database; not a HIPAA-compliant
production system.

## What this project does not claim

Not a HIPAA-compliant production system · not clinical decision support · does not
predict payer approvals/denials · no guaranteed savings or real revenue recovered
· no automated payer submission · not ready for real patient data.

## What would be required before a real clinic pilot

Legal, security, and compliance review; encryption in transit and at rest;
role-based access control; audit logging; data retention controls; monitoring;
and appropriate agreements (such as a BAA where applicable) before any real PHI.
See [`docs/commercialization_roadmap.md`](commercialization_roadmap.md).

## 60-second interview explanation

> "Plenara is a synthetic healthcare-operations analytics prototype. It takes
> three messy operational workflows — prior authorization, provider onboarding,
> and lab revenue-cycle claims — and turns them into one explainable readiness
> picture using READY / NEEDS REVIEW / BLOCKED states. I built deterministic
> Python rules for each workflow, generated realistic synthetic data with designed
> friction and aging, and layered analytics on top: a unified work queue with
> severity and recommended actions, executive KPIs and data-derived insights, and
> a DuckDB SQL portfolio that answers eight business questions and passes a
> consistency check against the Python logic. Streamlit is just the presentation
> layer — all the logic lives in reusable modules with tests and data-quality
> checks. It is deliberately synthetic-only with explicit safety boundaries: no
> PHI, no integrations, no predictions — human-in-the-loop workflow support that
> shows how this could become a real product later."
